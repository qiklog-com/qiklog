# Stage 3 — Accept OTLP logs over HTTP/protobuf

Branch: `feat/otlp-http-protobuf`, from `feat/otlp-http-json`.

Program decisions: [README](README.md). Mapping rules:
[02-otlp-http-json.md](02-otlp-http-json.md). This stage adds an encoding. It
does not add a second mapper.

## Problem

`http/json` is the easy encoding to test. The Collector's `otlphttp` exporter
sends `application/x-protobuf` unless someone flips it. That is the request
QikLog will actually see.

## Scope

- Same route, `Content-Type: application/x-protobuf`.
- Vendored `opentelemetry-proto` at one pinned tag, C# generated by
  `Grpc.Tools`.
- A protobuf adapter that fills the stage 2 internal model, then calls the
  stage 2 mapper.
- The stage 2 HTTP scenarios, parameterized over both encodings, plus one
  captured-bytes fixture.
- Update the www OTLP page so the recommended protocol is protobuf.

## Out of scope

- gRPC (stage 4). Do not add `Grpc.AspNetCore` or map `LogsService` yet.
- Editing generated C#.
- Changing JSON mapping, caps, status codes, or auth.
- Trace or metric protos beyond what the logs proto imports.
- Accepting `application/protobuf`. That type is **415**, same as any other
  unknown type.

## Proto

At the start of the stage, pin the latest stable release tag of
`github.com/open-telemetry/opentelemetry-proto`. Record in
`src/QikLog.Api/Otlp/proto/README.md`:

- tag and commit
- the Apache-2.0 license, with the upstream `LICENSE` file copied beside the
  protos
- the file list that was copied

Vendor only the logs collector proto and the protos it imports (common,
resource, logs). Do not vendor the whole repository.

Generate C# with `Grpc.Tools`. Packages: `Grpc.Tools` and `Google.Protobuf`
(see the README open question; do not start generation until that package is
allowed). `QikLog.Core` does not reference either package.

The adapter maps generated `LogRecord` / `ResourceLogs` messages onto the
stage 2 internal model. Field correspondence is the proto field, not a
reinvention:

- `time_unix_nano`, `observed_time_unix_nano`
- `severity_number`, `severity_text`
- `body` as `AnyValue`
- record `attributes` and resource `attributes`
- `trace_id` and `span_id` bytes rendered as lowercase hex
- scope `name`
- resource `service.name`

Hex from bytes must match hex from JSON for the same id. A 16-byte trace id
and an 8-byte span id are required; any other length omits that property and
still accepts the record, same as a bad JSON hex string.

## HTTP

`POST /otlp/v1/logs` with `Content-Type: application/x-protobuf`.

- Gzip, both size caps, auth, rate limit, usage, partial success, and 402
  behave as in stage 2.
- Success body is the protobuf `ExportLogsServiceResponse`. Content-Type
  `application/x-protobuf`. Full success is an empty message (no
  `partial_success` field). Partial success sets `rejected_log_records` and
  `error_message` with the same text the JSON encoder uses (`empty body`).
- Malformed or truncated protobuf is **400**
  `{ "error": "malformed OTLP protobuf" }`. The error body stays JSON, same
  as the other QikLog errors. Persist nothing.
- JSON requests still get JSON responses. Encoding of the response matches
  the request's content type.

## Conditions of Satisfaction

1. A protobuf body and the equivalent JSON body map through the same
   `LogEntry` rules. Severity bands, missing `service.name`, non-string
   bodies, trace ids, and caps match stage 2.
2. Every stage 2 API scenario holds for `application/x-protobuf`: 401, 403,
   402 for a batch that does not fit, gzip, wire-cap 413, decompress-cap
   413, partial success, history per source.
3. Truncated protobuf is 400 with `malformed OTLP protobuf` and persists
   nothing. JSON 400 behavior is unchanged.
4. A byte fixture captured from a real exporter is accepted and the known
   message shows up in history.
5. `QikLog.Core` has no protobuf reference. Mapping logic exists in one
   place; the adapter only converts messages into the internal model.
6. The www page recommends `http/protobuf` and still mentions JSON.
7. `application/protobuf` is 415.

## Scenarios

Stage 2 mapper tests stay encoding-agnostic. This stage adds parser tests
and parameterizes the HTTP tests.

### Parser agreement

Project: `tests/QikLog.Api.Tests` or a small adapter test next to the
generated code. Each scenario builds one JSON document and one protobuf
message with the same data, parses both into the internal model, and asserts
the models are equal. Then one mapper call (from the existing core tests'
expectations) is enough; do not re-implement the assertions.

#### 1. `Given_both_encodings_When_parsed_Then_severity_band_models_match`

Rows are the stage 2 severity table (1, 4, 5, 8, 9, 12, 13, 16, 17, 20, 21,
24) plus number 0 with text `ERROR`.

#### 2. `Given_both_encodings_When_service_name_missing_Then_models_match`

Resource attribute `deployment.environment=prod`, no `service.name`.

#### 3. `Given_both_encodings_When_body_is_not_a_string_Then_models_match`

Rows: bool, int, double, bytes `hi`, array of one string, kvlist of one
pair.

#### 4. `Given_both_encodings_When_trace_id_set_Then_hex_matches`

Uppercase hex in JSON and the same raw bytes in protobuf produce the same
lowercase `trace_id` and `span_id` on the model. A 3-byte trace id omits the
field in both.

#### 5. `Given_both_encodings_When_attributes_exceed_caps_Then_mapped_entries_match`

The stage 2 cap fixture, expressed in both encodings, mapped with default
caps, produces equal `LogEntry` values. This is the one place the cap
scenario is run for both encodings end to end through the mapper.

### API, both encodings

Parameterize stage 2 API scenarios 9 through 17 and 19 with
`application/json` and `application/x-protobuf`. The request body is the
encoding under test. Status codes, `rejectedLogRecords` / 
`rejected_log_records`, and history assertions are the same. JSON error
bodies (`error`, `usage`, `limit`) stay JSON even when the request was
protobuf, except the 200 body, which matches the request encoding.

Scenario 18 from stage 2 (protobuf → 415) is deleted, not parameterized.
Replace it with scenario 7 below.

#### 6. `Given_truncated_protobuf_When_posting_Then_400`

Covers COS 3.

- **Given** `Content-Type: application/x-protobuf` and a body of the single
  byte `0xFF`
- **When** the client POSTs it
- **Then** the response is 400, the JSON `error` is
  `malformed OTLP protobuf`, and history is unchanged

#### 7. `Given_application_protobuf_content_type_When_posting_Then_415`

Covers COS 7.

- **Given** `Content-Type: application/protobuf`
- **When** the client POSTs a body
- **Then** the response is 415

#### 8. `Given_captured_exporter_bytes_When_posting_protobuf_Then_message_is_in_history`

Covers COS 4.

- **Given** `tests/QikLog.Api.Tests/Fixtures/otlp-logs-export.bin`, captured
  from a named exporter and version recorded in
  `tests/QikLog.Api.Tests/Fixtures/otlp-logs-export.md`
- **When** the client POSTs those bytes as `application/x-protobuf` with a
  valid API key
- **Then** the response is 200 and history for the fixture's `service.name`
  contains the fixture's message
- **And** the fixture contains no API key and no Authorization header

Capture the fixture in this stage from a real exporter (the .NET OTLP log
exporter or `otelcol` `otlphttp`). Record the tool and version in the
sidecar markdown. Do not hand-build the bytes and call them a capture.

COS 5 is a test-project assertion that `QikLog.Core.csproj` does not
reference `Google.Protobuf`, plus review that the adapter has no severity
`switch`. COS 6 is `make www-build`.
